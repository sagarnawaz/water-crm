# Architecture

## Stack
| Part | Choice | Why |
|---|---|---|
| App | **Next.js (App Router) + TypeScript** | One codebase for the UI and server actions; free hosting on Vercel |
| Styling | **Tailwind CSS** | Fast mobile-first styling, no UI kit |
| Database + auth | **Supabase** (Postgres, Auth, RLS) | Login, database and tenant isolation in one place; plain Postgres, so little lock-in |
| Validation | **Zod** | One schema shared by forms and server actions |
| Hosting | **Vercel** | Preview URL per PR, production from `main` |

Not used: a separate API server, an ORM, a state library, a UI kit, payment SDKs.

## Multi-tenancy
- Every business is a row in `businesses`. Every data table has `business_id`.
- **Row Level Security on every table:**
  `business_id in (select business_id from memberships where user_id = auth.uid())`
- The `business_id` of a new row comes from a DB default/trigger based on the user's membership. It is never trusted from the client.
- An automated test proves that user A can't read or write business B's rows.

## Authentication
- **Phone number + password** (Supabase Auth).
- We create the accounts with the Supabase admin API and `phone_confirm: true`. No SMS is sent, so there is no SMS cost.
- No self sign-up in Phase 1. Password resets are done by us. SMS OTP reset is a later add-on.
- Phase 1 has one role, `owner`.

## Database schema
All money is `integer` rupees (no paisa, no floats). Every table has `created_at` and `updated_at`.

```sql
businesses   (id uuid pk, name text, default_rate int check (default_rate > 0), created_at)

floor_prices (business_id uuid fk, floor text, price int check (price > 0),
              primary key (business_id, floor))

memberships  (user_id uuid fk auth.users, business_id uuid fk, role text default 'owner',
              primary key (user_id, business_id))

customers    (id uuid pk, business_id uuid fk,
              house_no text not null, floor text not null, area text not null,
              name text, phone text,
              billing_type text check (billing_type in ('monthly','daily')),
              custom_rate int check (custom_rate > 0),        -- null = floor price
              default_qty int check (default_qty > 0),         -- null = on request
              opening_balance int default 0,
              opening_bottles int default 0 check (opening_bottles >= 0),
              active bool default true, notes text)
  unique index on (business_id, lower(trim(house_no)), lower(trim(floor)), lower(trim(area))) where active

deliveries   (id uuid pk,                                      -- generated by the client: idempotent
              business_id uuid fk, customer_id uuid fk,
              date date not null,
              qty int not null check (qty >= 0),
              empties_returned int not null check (empties_returned >= 0),
              rate int not null check (rate > 0),              -- price copied at entry time
              amount int generated always as (qty * rate) stored,
              note text, deleted_at timestamptz,
              check (qty + empties_returned > 0))
  index on (customer_id, date)                                 -- not unique: several deliveries per day allowed

payments     (id uuid pk,                                      -- generated by the client: idempotent
              business_id uuid fk, customer_id uuid fk,
              date date not null,
              amount int not null check (amount > 0 and amount <= 1000000),
              method text check (method in ('cash_rider','cash_owner','online')),
              for_month date check (for_month = date_trunc('month', for_month)),  -- 1st of the month; set for monthly customers, null for daily
              note text, deleted_at timestamptz)

audit_log    (id bigserial pk, business_id uuid, table_name text, row_id uuid,
              action text, old jsonb, new jsonb, user_id uuid, at timestamptz default now())
              -- written by a trigger on customers, deliveries, payments, floor_prices
```

Views (calculated, never stored; see [BUSINESS_RULES.md](BUSINESS_RULES.md#calculations)):
- `customer_balances`: balance and bottles at home for each customer.
- `ledger_lines`: deliveries and payments merged, with a running balance from a window function.
- `monthly_statements`: opening, bottles, empties, billed, paid, closing, and the bill's `paid_for` and `left`, per customer per month.

At about 100 customers × 30 rows a month, plain views are fast enough. If they ever get slow, add a materialized monthly table then.

## Validation (three layers)
1. **Zod** on the client, for instant messages.
2. The **same Zod schema** in the server action.
3. **DB constraints** (checks, unique indexes, RLS) as the final safety net.

## PWA and offline
- Web manifest, icons, and a minimal service worker that caches the app shell. Installable on Android Chrome and iOS Safari.
- **Phase 1 is online-only for saving.** Pages already loaded can still be viewed. When offline, the save buttons are disabled and an "Offline" banner is shown.
- Later: an IndexedDB outbox for offline entries. Client UUIDs are already the primary keys, so replaying saved entries can't create duplicates.

## Backup and data protection
- On the free tier, a nightly `pg_dump` runs from a GitHub Action to private storage, kept for 30 days. On the paid tier, Supabase daily backups.
- The owner has a **CSV export** of all customers, entries and payments in Settings.
- A restore is tested once before launch.
- Secrets are kept only in Vercel and GitHub environment settings. The service-role key never reaches the browser.

## Deployment
- GitHub → Vercel. Every PR gets a preview deploy; `main` deploys to production.
- Supabase migrations live in `supabase/migrations/` and run in CI before deploy.
- There are two Supabase projects: `staging` (for previews) and `production`.
